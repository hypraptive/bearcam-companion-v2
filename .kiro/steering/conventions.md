# BearCam Companion v2 — Coding Conventions

## File & Directory Structure

```
bearcam-companion-v2/
├── amplify/                    # Amplify Gen 2 backend (TypeScript)
│   ├── auth/resource.ts
│   ├── data/resource.ts
│   ├── storage/resource.ts
│   ├── functions/
│   │   ├── ingest-image/       # One directory per Lambda
│   │   ├── detect-objects/
│   │   └── compute-bear-list/
│   └── backend.ts
├── src/
│   ├── app/                    # Next.js App Router pages
│   │   ├── (public)/           # Route group: no auth required
│   │   │   ├── page.tsx        # Gallery / home
│   │   │   └── images/[id]/
│   │   ├── (auth)/             # Route group: requires login
│   │   └── admin/              # Admin-only pages
│   ├── components/
│   │   ├── ui/                 # shadcn/ui components (auto-generated, owned by project)
│   │   ├── bears/              # Bear-specific components (BoundingBox, IdentificationPanel, etc.)
│   │   ├── images/             # Image-specific components (ImageCard, ImageGrid, etc.)
│   │   └── layout/             # Nav, footer, page shells

│   └── types/                  # Shared TypeScript types not generated by Amplify
├── public/
└── amplify_outputs.json        # Generated — gitignored
```

## Naming Conventions

- **Files**: `kebab-case` for all files and directories (`image-card.tsx`, `compute-bear-list/`)
- **React components**: `PascalCase` named exports (`export function ImageCard()`)
- **Non-component exports**: `camelCase` (`export function formatBearList()`)
- **Types/interfaces**: `PascalCase`, no `I` prefix (`type BearIdentification`, not `IBearIdentification`)
- **Constants**: `SCREAMING_SNAKE_CASE` for module-level constants (`CAM_FEEDS`, `MIN_CONSENSUS_CONFIDENCE`)
- **GraphQL operations**: Named explicitly — `GetImageById`, `ListImagesByFeed`, `CreateIdentification`

## TypeScript

- Strict mode is on — no implicit `any`
- Explicit return types on all exported functions
- Use `type` over `interface` unless declaration merging is needed
- Prefer `unknown` over `any` when a type is genuinely unknown; add a type guard
- Use Amplify's generated types from `amplify_outputs.json` — do not manually duplicate model types
- Avoid type assertions (`as SomeType`) except when interfacing with untyped external APIs

## React & Next.js

- Prefer **Server Components** by default; add `'use client'` only when the component needs interactivity, browser APIs, or React hooks
- No default exports for components — use named exports consistently
- Keep components focused: one primary responsibility per file
- Co-locate component-specific types and helpers in the same file if small; extract to a separate file if they grow
- Use Next.js `<Image>` for all bear/webcam images — never raw `<img>` tags — to get automatic optimization
- Use Next.js `<Link>` for all internal navigation

## Styling

- Tailwind utility classes only — no inline `style` props, no CSS modules, no styled-components
- Mobile-first: write base styles for mobile, add `sm:` / `md:` / `lg:` overrides for larger screens
- Use the `cn()` utility (from `src/lib/utils.ts`) to merge conditional classes: `cn('base-class', condition && 'conditional-class')`
- Dark mode: use Tailwind's `dark:` variant; do not hardcode light-only colors
- Do not add custom colors or spacing to the Tailwind config without discussion — use the design token system from shadcn/ui

## API & Data Access

- All AppSync queries and mutations go through typed helper functions in `src/lib/amplify/`
- Never call the Amplify client directly from page or component files — always through the helpers
- Server Components fetch data server-side; Client Components use the Amplify client with `'use client'`
- Handle loading, error, and empty states explicitly — no silent failures
- Never modify `bearCount`, `bearList`, `consensusName`, `consensusConfidence`, or `totalVotes` from the frontend; these are Lambda-managed

## Lambda Functions

- TypeScript source for all functions (`amplify/functions/<name>/handler.ts`)
- AWS SDK v3 only — modular imports (`import { RekognitionClient } from '@aws-sdk/client-rekognition'`)
- Each function has a single, clearly named entry point: `export const handler`
- Log inputs and significant events with `console.log` (CloudWatch); log errors with `console.error`
- Never log sensitive values (user tokens, API keys)
- Functions should be idempotent where possible (safe to retry)

## Auth Checks

- Use the Amplify `fetchUserAttributes()` / `getCurrentUser()` helpers — do not parse JWT tokens manually
- Check admin status by inspecting the `cognito:groups` claim from the access token
- UI-level admin gates (hiding buttons, redirecting routes) are acceptable for UX, but they are never a substitute for API-level auth rules — both must exist
- The canonical admin check helper lives in `src/lib/amplify/auth.ts`

## Git & Commits

- Branch naming: `feature/<short-description>`, `fix/<short-description>`, `chore/<short-description>`
- Commit messages: imperative mood, present tense — "Add bear registry table", not "Added bears"
- Do not commit `amplify_outputs.json` or any `.env` files
